RAG From Scratch: Why I Wrote TF-IDF, BM25, and RRF by Hand

August 27, 2026 · 7 min read · Source code

Most RAG tutorials start with pip install langchain chromadb. I went the other way: I wrote the retrieval engine by hand — TF-IDF, BM25, and Reciprocal Rank Fusion — with zero dependencies. This post is about what I learned, and why the "boring" path made me a better engineer.

The problem: LLMs hallucinate facts

Ask a raw LLM about your shop's return policy and it will confidently invent one. For a business, that's fatal. The fix is RAG: retrieve the relevant knowledge, then let the LLM answer only from that context.

The pipeline:

Customer question
  → ① Retrieve   TF-IDF + BM25 dual retrieval + RRF re-rank
  → ② Assemble   Inject top chunks into the prompt
  → ③ Generate   DeepSeek answers from knowledge only

Three algorithms, written by hand

AlgorithmIdea in one lineWhy it matters
TF-IDFTerm frequency × inverse document frequency, cosine similarityIntuitive, explainable baseline
BM25Term frequency saturation + document length normalizationIndustry standard — same as Elasticsearch
RRFMerge ranked lists by reciprocal rankCombines strengths, more robust

BM25 in 20 lines

def bm25_score(query_terms, doc, doc_freqs, N, avg_dl, k1=1.5, b=0.75):
    dl = len(doc)
    score = 0.0
    for term in query_terms:
        tf = doc.count(term)
        if tf == 0:
            continue
        df = doc_freqs.get(term, 0)
        idf = math.log(1 + (N - df + 0.5) / (df + 0.5))
        tf_norm = (tf * (k1 + 1)) / (tf + k1 * (1 - b + b * dl / avg_dl))
        score += idf * tf_norm
    return score

The k1 and b parameters are the magic: k1 saturates term frequency (a word appearing 10× isn't 10× more important), and b penalizes long documents. Tuning these two numbers beats adding a vector database in many cases.

Chinese text: the jieba detour

My knowledge base is in Chinese — and Chinese has no spaces between words. "手机回收" could tokenize as ["手机", "回收"] or ["手", "机回", "收"]. I used jieba, a pure-Python segmenter, which solved it in one line. The lesson: language-specific preprocessing often matters more than the retrieval algorithm itself.

Query rewriting: the hidden 30% win

Customers don't type like search queries. They say "寄过来安全吗会不会被骗" ("is it safe to ship, will I get scammed"). The knowledge base says "付款安全" ("payment security"). These don't match.

Fix: before retrieving, ask a cheap LLM call to rewrite the casual question into 3-5 retrieval keywords. This lifted hit quality dramatically in my tests:

Customer: "寄过来安全吗会不会被骗"
Rewrite:  "付款安全 交易保障 防诈骗 流程"
→ hits payment-security doc #9 (was missing before)
💡 Insight: A 1-cent LLM call that rewrites the query can be worth more than a $100/month embedding API. Understand where your bottleneck actually is before spending money.

Then I added vectors (and why)

After the hand-written baseline worked, I upgraded to ChromaDB + bge-m3 embeddings + a bge-reranker cross-encoder for neural re-ranking. The hybrid pipeline:

BM25 (free, local) + bge-m3 (semantic)
  → bge-reranker (neural re-rank)
  → DeepSeek (generate)

The reranker is the real upgrade — it reads query+document pairs together, which pure embeddings can't do. But I wouldn't have understood why it's better without building the naive version first.

The takeaway

Build the boring version first. A hand-written BM25+RRF pipeline is free, fast, explainable, and gets you 80% of the way. Add vectors when you can measure the gap. In a world of copy-paste RAG stacks, being able to explain why each piece exists is a genuine differentiator — for your product, and for your interview.
