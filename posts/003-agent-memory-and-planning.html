Agents That Remember and Plan: Memory Systems and ReAct in Production

August 28, 2026 · 6 min read · Memory agent · Planner

Two capabilities separate a chatbot from an agent: memory (it knows you) and planning (it does things in steps). I built both into customer-service agents. Here's what actually worked.

Part 1: Memory — the agent that recognizes returning customers

The scenario: a customer bought a phone from you in March. In June, they come back asking about trade-in. A stateless chatbot starts from zero. A memory agent says: "Welcome back! Last time you bought an iPhone 13 Pro — I remember your preferred payment method was WeChat."

That one sentence changes the customer relationship. Here's the architecture:

Three-layer memory:
  ├─ Working memory    current conversation (short-term)
  ├─ Episodic memory   ChromaDB: customer profile + history
  │                    keyed by customer_id
  └─ Semantic memory   RAG knowledge base (product docs, policies)

Episodic memory in ChromaDB

Each customer interaction is upserted into a vector store keyed by customer_id. When the customer returns, the agent retrieves their history with exact-ID reads (not just semantic search) — so it knows the previous quote instead of guessing.

# Remember the quote the agent gave last time
collection.upsert(
    ids=[f"quote-{customer_id}-{quote_id}"],
    documents=[f"Quoted ¥{price} for {model} on {date}"],
    metadatas=[{"customer_id": customer_id}]
)

Graceful degradation

Real-world lesson: embedding APIs fail, quotas run out, networks drop. My agent falls back gracefully:

  • Embedding API down → use a local keyword matcher
  • Vector store unreachable → fall back to exact-ID history only
  • LLM timeout → retry with exponential backoff, then answer from retrieved context alone
💡 Production lesson: an agent that works with degraded infrastructure is worth more than a perfect one that crashes. Design fallbacks first.

Part 2: Planning — ReAct vs Plan-and-Execute

I implemented both patterns and measured the difference:

ReAct (Reason + Act)

Thought: customer wants a trade-in price for iPhone 13
Action: query_price(model="iPhone 13")
Observation: ¥3,100
Thought: also check depreciation
Action: calc_depreciation(...)
Observation: 12 months, 78% retention
Final: "Your iPhone 13 is worth about ¥3,100"

ReAct is flexible — the model decides the next step from the last observation. Great for open-ended tasks. Cost: many LLM round-trips.

Plan-and-Execute

Write the whole plan first, then execute steps, then summarize. Fewer LLM calls, cheaper for long tasks. I use ReAct for customer chat (unpredictable) and Plan-and-Execute for batch jobs (predictable).

Part 3: Cost optimization — cut API spend by 80%

Agents burn tokens. Three techniques that actually worked:

  1. Response caching — identical questions (warranty, shipping policy) hit the cache after the first call. Up to 90% savings on common questions.
  2. Model tiering — route simple questions to deepseek-chat (cheap), complex reasoning to deepseek-reasoner (expensive). Keyword classification picks the tier.
  3. Context trimming — send only relevant knowledge snippets, not the full manual. Tokens per request drop dramatically.
# Model tiering: cheap for simple, smart for complex
def pick_model(question):
    simple = ["warranty", "shipping", "hours", "price", "return"]
    if any(k in question.lower() for k in simple):
        return "deepseek-chat"      # $0.14/M tokens
    return "deepseek-reasoner"      # $0.55/M tokens

What I'd tell my past self

  • Memory beats context-window stuffing. A vector store is cheaper than 100k-token prompts.
  • ReAct for chat, Plan-and-Execute for jobs. Don't force one pattern everywhere.
  • Measure cost per conversation from day one. It's the metric that decides if your product survives.
