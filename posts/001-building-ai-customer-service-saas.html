Building a Multi-Tenant AI Customer Service SaaS with Zero Cloud Cost

August 28, 2026 · 8 min read · Source code

I've been building AI agents for a while. But there's a gap between an agent that works on my laptop and a product someone pays for. This post is about crossing that gap: turning three days of agent-building into a multi-tenant SaaS — with users, shops, orders, and simulated payments — running on a single Flask process with SQLite.

The problem with "AI that can chat"

My earlier agents could answer questions, remember customers, and even plan tasks. But they couldn't do three things that matter for a business:

  • No user system — anyone could use it, so nobody would pay.
  • No orders or payments — the AI could talk, but it couldn't close a deal.
  • Standalone scripts — no way to deploy for someone else.

The insight: an AI customer service agent only creates value when it's embedded in a business loop. Chat is the interface; the loop is: register → configure → serve customers → collect payment.

Architecture: one process, five tables

┌─────────────────────────────────────────────┐
│  Flask Web (app.py)                          │
│  ├─ User System    Register/Login/Token Auth │
│  ├─ Shop Management    Prices/Welcome/Plans  │
│  ├─ AI Customer Service    POST /api/chat    │
│  ├─ Order & Payment    Order→Pay→Callback    │
│  └─ Demo Console     Browser                 │
├─────────────────────────────────────────────┤
│  AI Engine (ai_engine.py)  Memory+Pricing+   │
│                          Purchase Intent     │
├─────────────────────────────────────────────┤
│  Database (db.py)  SQLite                   │
│   users / shops / orders / payments / msgs   │
└─────────────────────────────────────────────┘

Deliberately boring on purpose. No Kubernetes, no microservices, no message queue. A single Flask app with SQLite can handle the first 10,000 users of a product like this — and it costs $0/month to run.

The AI engine: memory + pricing + intent

The heart is ai_engine.py. It does three jobs:

  1. Remembers — each shop has its own conversation context, so the AI knows what the customer asked 10 minutes ago.
  2. Quotes prices — reads the shop owner's price list, so the AI never invents a price. This is the trust-killer most chatbots fail at.
  3. Detects purchase intent — when the customer says "I want to buy it", the engine returns a structured action, and the backend creates an order.
💡 Design lesson: the AI doesn't decide whether to create an order — it returns intent, and the backend decides. This keeps money flows deterministic and auditable. Never let the LLM be the source of truth for financial state.

Multi-tenant isolation done simply

Every table has a shop_id. Every query filters by it. That's it. For a product at this stage, row-level scoping beats complex tenant-per-database setups — you can migrate later when a real customer demands it.

The payment state machine

Orders flow through pending → paid. The payment endpoint is idempotent: calling it twice doesn't double-charge. This is the kind of detail that separates a demo from a product.

# Idempotent payment: same order, same result
def pay_order(order_id, user_id):
    order = get_order(order_id)
    if order.status == 'paid':
        return order  # already paid, no double-charge
    order.status = 'paid'
    save(order)
    return order

What I'd do differently

  • Real payments — WeChat Pay / Stripe instead of simulation. The interface is already clean, so swapping is a day of work.
  • Rate limiting — LLM calls cost money; per-shop daily quotas are essential before real customers.
  • Async processing — for long conversations, a queue (Redis or even SQLite-backed) would help.

Why this matters for an indie developer

The bar for shipping a real product is lower than most people think. One process, five tables, one LLM API — and you have a business. The hard part isn't the tech; it's deciding what loop to close. AI + a payment loop is the most direct path from code to revenue I know.
